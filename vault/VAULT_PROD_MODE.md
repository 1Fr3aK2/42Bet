# Vault Production Mode (`vault/`)

This document describes moving HashiCorp Vault out of dev-mode into a
persistent, TLS-secured setup, for the WAF/ModSecurity + Vault module
(secrets "encrypted and isolated").

## Overview

Vault previously ran as `vault server -dev`: everything (secrets, policies,
the AppRole setup) lived only in memory and was wiped on every container
restart. This didn't meet the subject's requirement of encrypted, isolated
secret storage, and was fragile — a crash mid-demo would lose all backend
credentials.

Vault now runs with:
- **Raft storage** — persistent, encrypted-at-rest, HashiCorp's current
  recommended backend (the older `file` backend is in maintenance mode).
- **Internal TLS** — the Vault API is served over HTTPS even for
  container-to-container traffic. The subject explicitly allows unencrypted
  internal traffic (Postgres, Redis do this), but Vault holds the most
  sensitive secrets in the system, so this is a deliberate
  defense-in-depth choice beyond the minimum requirement.
- **Automatic init + unseal** — handled by `vault-init.sh`, so the stack
  still comes up with a single `docker compose up -d`.

## Files

```
vault/
├── config/
│   ├── vault.hcl            # server config: raft storage, TLS listener
│   ├── backend-policy.hcl   # read-only ACL policy for the backend
│   └── vault-init.sh        # init / unseal / secrets / AppRole setup
└── certs/                   # generated by setup-certs.sh, not committed
    ├── vault.cert
    ├── vault.key
    └── ca.pem
```

See `vault.hcl`'s own documentation for the storage/listener config details,
and `backend-policy.hcl`'s for the ACL policy.

## TLS certificates

`setup-certs.sh` (already used for the Nginx certificate) was extended to
also generate one for `vault`, reusing the same local mkcert CA — so a
single `mkcert -install` covers both. The CA root is copied to
`vault/certs/ca.pem`, which every client (backend, `vault_init`) needs to
trust the self-signed certificate.

## Docker Compose changes

- `vault` service: `command` changed from `vault server -dev` to
  `vault server -config=/etc/vault/config/vault.hcl`; added
  `cap_add: [IPC_LOCK]` with `ulimits.memlock: -1` (mlock needs both the
  capability and an unlimited ulimit — the capability alone isn't enough);
  new `vault-data` volume for the raft storage.
- `vault_init` service: no longer takes a fixed `VAULT_TOKEN` — the script
  now reads the root token from its own init output instead.
- Two new one-shot `alpine` init containers (same pattern as the existing
  `prometheus-init`) `chown` the `vault-data` and `vault-keys` volumes to
  the `vault` user (UID 100) before the main containers start — Docker
  volumes default to `root` ownership, but the Vault process doesn't run as
  root.
- `backend` service: gained `VAULT_ADDR`/`VAULT_CACERT` (now `https://` and
  a CA path, not `http://`) and a read-only mount of `vault/certs`, plus a
  read-only mount of the `vault-approle` volume — see "AppRole credential
  persistence" below. `backend_seed` gained the same three mounts, since it
  also needs to authenticate to Vault (to read the admin account credentials
  it seeds) before the main `backend` service starts.

## `vault-init.sh` changes

The script handles, in order:

1. **`vault operator init`** — runs only once. Guarded by checking whether
   `/vault/keys/init.json` (on the `vault-keys` volume) already exists, since
   Vault refuses to be initialized twice.
2. **`vault operator unseal`** — runs on every start where Vault reports
   `sealed: true` (i.e., every restart, since dev-mode's auto-unseal no
   longer applies). Uses 3 of the 5 generated Shamir key shares, read from
   the same `init.json`.
3. **Bootstrap-already-done check** — see "Idempotent bootstrap and root
   token revocation" below. New since the previous revision of this
   document.
4. **Enabling the `secret/` KV v2 engine** — dev-mode auto-mounts this;
   production mode doesn't, so it has to be enabled explicitly
   (`vault secrets enable -path=secret -version=2 kv`), idempotently.
5. 5. **Storing the six secrets** (Postgres, Redis, admin API key, admin
   account, JWT secret, Elasticsearch monitoring user). The Postgres entry holds the credentials of
   `app_user`, the backend's least-privilege database role (audit finding
   S9), not those of the `POSTGRES_USER` superuser — see
   `postgres/init/ensure-app-user.sh`.
6. **Loading the policy** (`backend-policy`) and **enabling AppRole**.
7. **Creating `backend-role`**, with `secret_id_ttl=0` — see below.
8. **Writing `role_id` and `secret_id`** to `/vault/approle`.
9. **Revoking the root token** — new since the previous revision; see below.

JSON parsing (root token, unseal keys) uses `grep`/`sed`/`cut` rather than
`jq` — `jq` isn't in the base image, and installing it at runtime via `apk
add` isn't reliable in this environment (network access from inside the
container can't be assumed).

## AppRole credential persistence

Originally, the AppRole `role_id`/`secret_id` pair generated by
`vault-init.sh` was only ever printed to the container's stdout — visible via
`docker compose logs vault_init`, but not actually consumable by the
`backend` service, since nothing wrote it anywhere the backend could read it.
In practice this meant the credentials had to be copied out manually, which
isn't compatible with the project's single-command startup requirement and
doesn't survive a rebuild.

Fixed by having `vault-init.sh` write both values to files on the
`vault-approle` volume (e.g. `/vault/approle/role_id`,
`/vault/approle/secret_id`), which `backend` and `backend_seed` both mount
read-only and read directly at startup to perform their own AppRole login —
no manual step, and no credential visible outside the container boundary
(not even in `docker compose logs`, now that it's written to a file instead
of printed).

## `secret_id` no longer expires

**Changed from the previous revision.** `backend-role` was created with
`secret_id_ttl=24h`, meaning any backend instance staying up for more than a
day would be rejected on its next AppRole login attempt — flagged as a known
limitation requiring either periodic renewal or a `vault_init` re-run.

This has been changed to `secret_id_ttl=0` (never expires). This removes
that limitation entirely for a project of this scope, at the cost of a
longer-lived credential if the `vault-approle` volume were ever compromised.
Given the credential is only ever persisted inside the Docker volume
boundary (never logged, never leaves the host), this trade-off was judged
acceptable here — worth revisiting if this setup were ever adapted for a
real multi-host deployment.

## Idempotent bootstrap and root token revocation

**New since the previous revision of this document**, and the most
behaviorally significant change in this update.

After the six secrets, the policy, and the AppRole are provisioned
(steps 4–8 above), the script now **revokes the Vault root token it used to
do all of this** (`vault token revoke`). This closes a real gap noted
previously only as an accepted limitation ("the root token should be
revoked in a real deployment after setup") — it is now actually done,
automatically, every time.

To make this safe across restarts, a new check runs right after unsealing
(step 3), before anything else:

- The script attempts `vault token lookup` using the root token read from
  `init.json`.
- **If that succeeds** (first-ever run, or any run before the token was
  revoked), the script proceeds normally through provisioning and then
  revokes the token at the end, same as before.
- **If it fails** (the root token was already revoked by a previous
  successful run) **and** `role_id`/`secret_id` already exist on the
  `vault-approle` volume, the script treats bootstrap as already complete
  and exits `0` immediately — steps 4–9 are skipped entirely.
- **If it fails and the AppRole files are missing**, this is treated as an
  inconsistent state (a revoked root token but no provisioned AppRole,
  which shouldn't normally happen) and the script exits `1` with a message
  pointing at `docker compose down -v` as the recovery path.

### Practical consequence: updating a secret value after the first bootstrap

Before this change, the pattern established earlier in this project for
syncing a changed `.env` value into Vault was: re-run `vault_init`
(`docker compose up -d vault_init`), since every step, including `vault kv
put`, ran unconditionally and idempotently on every invocation.

**This is no longer sufficient once bootstrap has completed once and the
root token has been revoked** — a subsequent `vault_init` run now exits
early at the bootstrap-check step and never reaches the `vault kv put`
calls, so a changed `.env` value (e.g. a rotated `JWT_SECRET`) will **not**
be picked up by just re-running `vault_init` anymore.

The correct way to update a secret now, without a full volume wipe, is to
generate a fresh root token using the unseal key shares (still valid —
revoking the root token does not invalidate the unseal keys), then use it
directly. On Vault 2.x, generating that token requires a temporary
configuration change first — see "Recovering a root token on Vault 2.x"
below.

#### Recovering a root token on Vault 2.x

Since Vault 2.0.0 (CVE-2026-5807, HashiCorp bulletin HCSEC-2026-08),
`sys/generate-root` is no longer unauthenticated: in addition to the unseal
key shares, it requires a valid Vault token. Because this project revokes
the root token at the end of the bootstrap, a plain
`docker compose exec vault vault operator generate-root -init` fails on
Vault 2.x with:

```
Code: 403. Errors:
* permission denied
```

This error is returned by Vault itself — the request goes straight to
`https://vault:8200`, bypassing Nginx and the WAF. It was reproduced on
Vault v2.0.4 and v2.2.1.

HashiCorp's supported workaround is the `enable_unauthenticated_access`
setting, a **list** of endpoint names (`"generate-root"`, `"rekey"`,
`"generate-operation-token"`) for which the previous unauthenticated
behavior is restored. Enable it only for the duration of this procedure:

1. Add this line to the top level of `vault/config/vault.hcl`. It must be a
   list: `enable_unauthenticated_access = true` is rejected and Vault fails
   to start with `unknown slice type`.

   ```hcl
   enable_unauthenticated_access = ["generate-root"]
   ```

2. Restart Vault so it re-reads the file, and unseal it again (see
   "Operational Note: Vault Restarts" below):

   ```bash
   docker compose restart vault
   docker compose up -d vault_init
   ```

3. Start the root token generation and note the `Nonce` and the `OTP`:

   ```bash
   docker compose exec vault vault operator generate-root -init
   ```

4. Submit 3 of the 5 unseal key shares (`unseal_keys_b64` in `init.json` on
   the `vault-keys` volume), one per command. When the key is passed as an
   argument, the `-nonce` flag is required; alternatively, run the command
   without arguments and paste each key at the hidden prompt. `Progress`
   goes `1/3`, `2/3`, `3/3`:

   ```bash
   docker compose exec vault vault operator generate-root -nonce=<nonce> "<unseal_key>"
   ```

5. After the third key, the output contains an `Encoded Token`. Decode it
   with the OTP from step 3:

   ```bash
   docker compose exec vault vault operator generate-root \
     -decode=<encoded_token> -otp=<otp>
   ```

   The result (`hvs....`) is the new root token. To abort an in-progress
   generation and start over, use `vault operator generate-root -cancel`;
   the nonce and OTP of the cancelled attempt are no longer valid.

6. Use the token (see "Updating the secret" below), then clean up: revoke
   it, remove the `enable_unauthenticated_access` line from `vault.hcl`,
   and restart and unseal Vault again.

   ```bash
   docker compose exec -e VAULT_TOKEN=<new_root_token> vault vault token revoke -self
   ```

   If a generation was started and not completed, cancel it **before**
   removing the line (`docker compose exec vault vault operator
   generate-root -cancel`): once the setting is gone, the cancel request
   needs a token like any other call to this endpoint.

> **Warning:** while `enable_unauthenticated_access` is set, anyone who can
> reach the Vault API can start or cancel a root token generation and block
> operators from completing it — the denial of service that Vault 2.0.0
> fixed. Keep the setting only for the duration of this procedure and never
> commit it to the repository.

`init.json` also contains the (already revoked) initial root token and all
the unseal key shares; treat its contents as sensitive and do not paste them
into issues, pull requests or chats.

#### Updating the secret

With the new root token:

```bash
docker compose exec vault sh -c 'VAULT_TOKEN=<new_root_token> vault kv put secret/jwt secret="<new_value>"'
```

A full `make re` (which wipes `vault-data`/`vault-keys`/`vault-approle`
entirely and re-initializes from scratch) remains the simpler option when a
clean slate is acceptable — see `DISASTER_RECOVERY.md` §4 for that scenario.
This section exists so the *other* option (updating one secret without
wiping everything) isn't a dead end now that the root token is gone by
default.

**This also applies to the S9 change** (least-privilege database role).
`secret/postgres` now holds the credentials of `app_user`, written by
`vault-init.sh` from `APP_DB_USER` / `APP_DB_PASSWORD`. On an environment
whose Vault was bootstrapped *before* that change, re-running `vault_init`
will not rewrite the secret, so the backend keeps connecting with the old
(superuser) credentials until the secret is updated with the procedure above
(`vault kv put secret/postgres user="<app_user>" password="<password>"`) or
the stack is rebuilt with `make re`. The `postgres_app_user_init` service
creates the database role on its own on every `docker compose up`, so only
the Vault side needs this manual step.

**The same applies to `elasticsearch-monitor`** (the `es_monitor` health-check
user). On an environment whose Vault was bootstrapped before this change,
`vault_init` exits early, so neither `secret/elasticsearch-monitor` nor the
updated `backend-policy` is provisioned, and `loadSecretsFromVault()` throws
when it cannot read the secret, so the backend cannot finish its bootstrap.
`ES_MONITOR_PASSWORD` must also be set in `.env`, otherwise
`elasticsearch_ilm_init` exits on its first line. The path verified for this
change is a full `make re`, which re-initializes Vault from `.env`.

## Operational Note: Vault Restarts

The `vault_init` service only runs once per container lifecycle — it
performs the unseal when *it* starts, not automatically every time the
`vault` container itself restarts independently. In this setup, recovering
from a manual `vault` container restart requires re-running
`docker compose up -d vault_init`. This is expected behavior for a
script-based unseal mechanism without a cloud KMS or HSM auto-unseal.

As of the root-token-revocation change above, re-running `vault_init` after
a `vault` restart now does exactly two things if bootstrap already
completed: unseal Vault, and exit — it does **not** re-provision secrets,
the policy, or the AppRole, since steps 4–9 are skipped. This is intentional
(nothing needs re-provisioning on a simple restart, since none of that data
was lost — only the in-memory seal state was), but worth knowing so the
early exit isn't mistaken for a failure when checking `docker compose logs
vault_init`.

## Issues found and fixed while testing

Testing this end-to-end (rather than assuming the config was correct)
surfaced several real bugs:

1. **`vault.hcl` typos** — `adress` instead of `address`, and
   `disable_mock` instead of `disable_mlock`. Vault silently ignores unknown
   config fields (only logging a warning), so `disable_mlock` was never
   actually set — which is fatal on the Vault version in use, where it no
   longer has a default.
2. **Healthcheck deadlock vs sealed detection** — `vault status` exits with
   code `2` whenever Vault is sealed or uninitialized, which Docker's
   healthcheck treats as failure. Earlier this was worked around by accepting
   any exit code other than 1 (`[ $? -ne 1 ]`), but that masked the sealed state:
   restarting Vault left it sealed while Docker still marked it `healthy`,
   letting the backend start and crash with `503 Vault is sealed`.
   Properly resolved by:
   - Setting the Vault healthcheck to `test: ["CMD", "vault", "status"]` (so
     sealed or failing states correctly report `unhealthy`).
   - Changing `vault_init`'s dependency to `depends_on: vault: condition: service_started`
     with a readiness wait loop in `vault-init.sh`, breaking the cycle without
     masking Vault's true operational health.
3. **`mlock` failing under `cap_add: IPC_LOCK` alone** — Docker also
   enforces a `memlock` ulimit, defaulting to a low value regardless of
   granted capabilities. Fixed by adding `ulimits.memlock: {soft: -1, hard:
   -1}` alongside the existing capability.
4. **Volume permission errors** (`permission denied` on both
   `/vault/data` and `/vault/keys`) — Docker-created named volumes default
   to `root` ownership; the Vault process runs as UID 100. Fixed with
   dedicated one-shot `chown` init containers, same pattern as the existing
   `prometheus-init`.
5. **`jq: not found`** — the base image doesn't include `jq`, and installing
   it at container start via `apk add` failed silently in this environment.
   Rewrote the JSON parsing in `vault-init.sh` using only `grep`/`sed`/`cut`.
6. **Missing `secret/` mount** — `vault kv put` failed with a `403` on
   the CLI's preflight capability check, even using the root token. Root
   cause: dev-mode auto-mounts a KV v2 engine at `secret/`; production mode
   doesn't. Fixed by explicitly enabling it in `vault-init.sh`.
7. **Duplicate `VAULT_ADDR` in `.env`** — an old `http://0.0.0.0:8200` line
   was left in `.env` alongside the new `https://vault:8200` one. `.env`
   files silently use the *last* definition of a duplicated key, so Vault's
   own healthcheck kept using the stale HTTP value — producing a stream of
   `TLS handshake error: client sent an HTTP request to an HTTPS server`
   that looked like a client-code problem but was actually a config file
   duplicate. **This is also the reason any plain-`http://` request to port
   `8200` now fails at the TLS/protocol level rather than reaching Vault's
   application-level ACL check** — relevant to anyone re-running
   `SECURITY_TESTING.md`'s Vault test against the current setup; see the note
   added there.
8. **Backend's own Vault client** (`health.service.ts`, `checkVault()`) had
   `http://vault:8200` hardcoded and no CA configured on its HTTP client,
   so it kept failing to reach the now-HTTPS Vault, surfacing as `/health`
   returning `503`. Fixed by reading `VAULT_ADDR`/`VAULT_CACERT` from the
   environment and passing an `https.Agent` with the CA to the request —
   deliberately not using `VAULT_SKIP_VERIFY`/disabling verification, which
   would have defeated the purpose of adding TLS in the first place.
9. **AppRole credentials only ever logged, never persisted** — see "AppRole
   credential persistence" above; fixed by writing `role_id`/`secret_id` to
   the `vault-approle` volume instead of relying on `docker compose logs`.
10. **`generate-root` returning `403` on Vault 2.x** — found while testing
    the S9 change on an existing environment. Not a bug in this project:
    Vault 2.0.0 made `sys/generate-root` require a valid token. The
    documented procedure was updated instead — see "Recovering a root token
    on Vault 2.x" above.

## How to test

1. `docker compose down -v && docker compose up -d` (a clean start exercises
   the full init/unseal/bootstrap/revoke path, not just a restart — note the
   `-v` is now relevant: a stale root token from a previous bootstrap would
   otherwise make step 3 below misleading).
2. `docker compose exec vault vault status` — expect `Initialized: true`,
   `Sealed: false`, `Storage Type: raft`.
3. `docker compose logs vault_init` — expect to see secrets written, the
   policy loaded, AppRole enabled, a RoleID/SecretID pair generated, and
   finally the root token revoked, with no errors. Additionally, confirm
   the credentials were actually persisted (not just logged):
   `docker compose exec backend sh -c 'cat /vault/approle/role_id'`
   should return a value, not an empty string or a "no such file" error.
4. `docker compose exec backend wget -qO- http://localhost:8000/health` —
   expect `{"status":"ok","database":"up","redis":"up","vault":"up"}`.
5. `docker compose ps` — `vault` and `backend` both `healthy`.
6. Restart resilience: `docker compose restart vault`, then
   `docker compose up -d vault_init` — confirm it detects the sealed state
   and unseals automatically without re-running `vault operator init`.
7. **New: idempotent skip behavior.** Run `docker compose up -d vault_init`
   a second time (without restarting `vault` itself, root token already
   revoked from step 1–3) — expect the log to show only the "bootstrap
   already complete" message and an immediate exit, with no secrets
   rewritten, no policy reloaded, and no new AppRole credentials generated
   (`role_id`/`secret_id` file contents unchanged from before this run).
8. **Backend uses the least-privilege database role (S9).** With the stack
   up, confirm the backend connects as `app_user`:
   `docker compose exec postgres sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB -c "SELECT usename, count(*) FROM pg_stat_activity WHERE datname = current_database() GROUP BY usename;"'`
   — an `app_user` row must appear.
9. **Root token recovery on Vault 2.x.** On the clean start from step 1
   (root token already revoked): `docker compose exec vault vault operator
   generate-root -init` must return `403 permission denied`. Then follow
   "Recovering a root token on Vault 2.x" — with
   `enable_unauthenticated_access = ["generate-root"]` set, `-init` must
   return a `Nonce` and an `OTP`, and after 3 unseal keys and the decode
   step the new token must show the `root` policy
   (`docker compose exec -e VAULT_TOKEN=<new_root_token> vault vault token
   lookup`). Finish by revoking the token and removing the setting, and
   confirm `-init` returns `403` again.
